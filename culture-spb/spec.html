1. Обзор проекта

1.1. Проблема

Информация о выставках изобразительного искусства в Санкт-Петербурге разбросана по десяткам источников: сайты музеев, телеграм-каналы об искусстве, порталы-агрегаторы (Афиша, Собака и т.д.). Нет единого места, где вся эта информация была бы собрана, нормализована и представлена в удобном виде.

1.2. Решение

Culture SPB — платформа-агрегатор, которая:
  • Автоматически собирает информацию о выставках из множества источников
  • Нормализует её в единый формат с помощью LLM
  • Дедуплицирует события
  • Публикует в телеграм-канал и на веб-портал
  • Поддерживает каталог площадок, художников и выставок (НСИ)

1.3. Целевая аудитория (фаза 1)

Ограниченная группа пользователей — любители искусства Санкт-Петербурга, заинтересованные в оперативном получении консолидированной информации о выставках.

1.4. География и тематика

  • Город: Санкт-Петербург (архитектура должна допускать расширение на другие города)
  • Тематика: Выставки изобразительного искусства (живопись, графика, скульптура, фотография, инсталляции, медиа-арт и т.д.)

5. Источники данных

5.1. Типы источников

5.1.1. Сайты музеев и галерей (~100–200 площадок)

Примеры: hermitagemuseum.org, rusmuseum.ru, erarta.com, bofreyart.com, и т.д.

Метод сбора: HTTP-скрейпинг + LLM-экстракция.

Для каждого сайта хранится конфигурация:

  • URL раздела «Выставки» / «Афиша»
  • Метод парсинга: llm_extract (страницу целиком отправляем в LLM) или css_selectors (структурированный парсинг + LLM для обогащения)
  • На этапе bootstrap — начинаем с llm_extract для всех, оптимизируем по мере необходимости
Почему LLM-экстракция как дефолт:
  • Сайты музеев имеют разную структуру, писать парсер под каждый — дорого
  • LLM отлично справляется с извлечением структурированных данных из HTML/текста
  • При изменении дизайна сайта LLM-парсер продолжает работать (в отличие от CSS-селекторов)

5.1.2. Телеграм-каналы

Примеры: @spb_afisha, @artpetersburg, каналы конкретных галерей и т.д.

Метод сбора: Telethon (userbot-клиент для чтения публичных каналов).

Процесс:

  • Подключаемся к публичным каналам
  • Раз в день забираем новые посты за последние 24 часа
  • Текст + изображения отправляются в пайплайн обработки
Важно: Используем только чтение публичных каналов. Не вступаем, не взаимодействуем. User account (не bot API) нужен для чтения каналов без вступления.

5.1.3. Сайты-агрегаторы

Список агрегаторов расширяемый — новые источники добавляются через админку или обнаруживаются автоматически (раздел 7). Ниже — примеры известных агрегаторов для начального bootstrap:

6.2. Этап 1: Сбор (Scraping)

Расписание: Ежедневно, ночью (03:00–05:00 MSK), чтобы все источники обновились за день. Для каждого активного Source:
  • Скачать контент (HTTP GET / Telethon fetch)
  • Сохранить в RawEvent со статусом new
  • Сохранить изображения (скачать, положить в object storage)
  • Записать last_scraped_at в Source
Обработка ошибок:
  • При ошибке HTTP — retry 3 раза с exponential backoff
  • При 3+ днях подряд ошибок — пометить Source как проблемный, уведомить в админке
  • Rate limiting: пауза 2-5 сек между запросами к одному домену

6.3. Этап 2: Фильтрация релевантности (LLM)

Задача: Определить, относится ли собранный контент к выставкам изобразительного искусства в Санкт-Петербурге. LLM-промпт (концепт):

``

Ты — классификатор культурных событий. Определи, относится ли следующий текст

к выставке изобразительного искусства в Санкт-Петербурге.

Релевантно: выставки живописи, графики, скульптуры, фотографии, инсталляций,

медиа-арта в музеях, галереях и выставочных пространствах Санкт-Петербурга.

НЕ релевантно: концерты, спектакли, лекции (если не привязаны к выставке),

события в других городах, продажа произведений искусства (аукционы),

мастер-классы без привязки к выставке.

Текст:

{raw_content}

Ответ в JSON:

{

"is_relevant": true/false,

"confidence": 0.0-1.0,

"reason": "краткое пояснение"

}

` Пороги:
  • confidence >= 0.8 → автоматически relevant
  • confidence < 0.3 → автоматически not relevant
  • Между 0.3 и 0.8 → на ручную модерацию (на этапе тестирования — всё на модерацию)
Результат: Обновление RawEvent.is_relevant, relevance_reason, статус → filtered

6.4. Этап 3: Нормализация и тегирование (LLM)

Задача: Из сырого контента извлечь структурированные данные в формате Exhibition. LLM-промпт (концепт): `

Извлеки информацию о выставке из следующего текста.

Если информация отсутствует — оставь поле null.

Если в тексте несколько выставок — верни массив.

Текст:

{raw_content}

Верни JSON:

{

"exhibitions": [

{

"title": "string",

"venue_name": "string — название площадки",

"venue_address": "string или null",

"date_start": "YYYY-MM-DD или null",

"date_end": "YYYY-MM-DD или null",

"artists": ["string — имена художников"] или [],

"description": "string — полное описание",

"description_short": "string — 1-2 предложения",

"type": "solo/group/permanent/other",

"tags": ["string — жанр, стиль, эпоха, техника"],

"image_description": "string — описание главного изображения, если есть"

}

]

}

Правила тегирования:

  • Жанр: живопись, графика, скульптура, фотография, инсталляция, медиа-арт,
декоративно-прикладное, смешанная техника
  • Стиль (если определим): импрессионизм, авангард, современное искусство,
реализм, абстракция и т.д.
  • Эпоха (если определим): античность, средневековье, XVIII век, XIX век,
XX век, современность ` Дополнительно:
  • Связывание venue_name с существующей площадкой в каталоге (fuzzy match по названию)
  • Если площадка не найдена — создать новую запись со статусом pending (требует подтверждения в админке)
  • Связывание художников — аналогично: поиск по имени, создание при отсутствии
Результат: RawEvent.normalized_data заполнен, статус → normalized

6.5. Этап 4: Проактивное обогащение (Proactive Enrichment)

Задача: Когда информация о выставке получена из вторичного источника (телеграм-канал, агрегатор), система проактивно обращается к первоисточнику — сайту площадки — для получения полных и достоверных данных. Процесс:
  • После нормализации определяется площадка (venue_id)
  • Если источник RawEvent — не сайт самой площадки (т.е. Source.type != website_museum):
a. Найти Source типа website_museum для этой площадки

b. Загрузить страницу выставок площадки

c. LLM-экстракция: найти на странице информацию о конкретной выставке (по названию / датам)

d. Мерж данных: дополнить/уточнить нормализованные данные из первоисточника

  • Если площадка ещё не имеет привязанного Source — пометить для ручного добавления
Приоритет данных при мерже:
  • Сайт площадки > агрегатор > телеграм-канал
  • При конфликте дат — берём с сайта площадки
  • Описание — берём самое полное (или мержим)
  • Изображение — приоритет у первоисточника (обычно лучшее качество)
Реактивное обогащение (Enrichment при повторных упоминаниях):

Когда новый RawEvent при дедупликации сопоставляется с уже существующей Exhibition:

  • Сравниваем поля: если в новом источнике есть данные, отсутствующие в текущей записи → дополняем
  • Если данные конфликтуют → применяем приоритет источников (см. выше)
  • Логируем все изменения для аудита
  • При существенных изменениях (смена дат, площадки) → создаём FeedPost типа update
Результат: Обогащённые данные с максимальной полнотой и достоверностью.

6.6. Этап 5: Дедупликация

Двухуровневая стратегия: Уровень 1 — Эвристический (быстрый):
  • Совпадение venue_id + нечёткое совпадение title (Levenshtein distance ≤ 0.2) + пересечение дат → вероятный дубликат
  • Совпадение venue_id + совпадение хотя бы одного художника + пересечение дат → вероятный дубликат
Уровень 2 — LLM (для неочевидных случаев): `

Определи, описывают ли эти два текста одну и ту же выставку:

Выставка A: {title_a}, {venue_a}, {dates_a}, {description_a}

Выставка B: {title_b}, {venue_b}, {dates_b}, {description_b}

Ответ: { "is_duplicate": true/false, "confidence": 0.0-1.0, "reason": "..." }

` При обнаружении дубликата:
  • Мержим данные: дополняем недостающие поля из нового источника
  • Добавляем source_url в массив источников выставки
  • RawEvent.duplicate_of → ссылка на оригинал
  • Статус → deduplicated

6.7. Этап 6: Модерация

Режим тестирования (начальный):
  • Все нормализованные события попадают в очередь модерации
  • Модератор в админке: Approve / Reject / Edit & Approve
  • При Approve → Exhibition.moderation_status = approved, is_published = true
Рабочий режим (после стабилизации):
  • Автопубликация для событий с relevance_confidence >= 0.8 от надёжных источников (Source.reliability_score >= 0.7)
  • Остальное — в очередь модерации
  • Возможность скрыть/отредактировать любую выставку через админку в любой момент

6.8. Этап 7: Формирование постов (Feed Generation)

Типы постов:
ТипТриггерРасписание
new_exhibitionНовая выставка одобренаПосле модерации / автоматически
updateСущественное обновление (изменение дат, площадки)После обнаружения
ending_soonВыставка заканчивается в течение 7 днейВоскресенье, утро
digestЕженедельный дайджест «Заканчивается на этой неделе»Воскресенье, 10:00 MSK
Формат нормализованного поста (для Telegram): `

🎨 {Название выставки}

📍 {Площадка}

📅 {Дата начала} — {Дата окончания}

👤 {Художник(и)} (если есть)

{Краткое описание — 2-3 предложения}

🏷 {теги через #}

🔗 Подробнее: {canonical_url на веб-портале}

` Формат дайджеста «Заканчивается на этой неделе»: `

⏰ Заканчиваются на этой неделе

  • 🎨 {Название} — до {дата}
📍 {Площадка}
  • 🎨 {Название} — до {дата}
📍 {Площадка}

...

Не пропустите! Полный список: {url}

`

Дайджест публикуется и закрепляется (pin) в канале. Предыдущий дайджест открепляется.

6.9. Этап 8: Публикация

Телеграм:
  • Публикация через Telegram Bot API
  • Пост: изображение (если есть) + текст + inline-кнопка «Подробнее» (ссылка на веб)
  • Дайджест: текст + pin
Веб-портал:
  • Регенерация статических страниц после завершения пайплайна (SSG build)
  • Обновление поискового индекса

6.10. Автоматическое обновление статусов выставок

Ежедневный cron job:

  • announced → running (если date_start <= today)
  • running → ending_soon (если date_end - today <= 7 days)
  • ending_soon → ended (если date_end < today)

7. Автообнаружение источников и bootstrap каталога

Разовый процесс при запуске проекта + еженедельное обновление.

7.1. Шаг 1: Seed-каталог площадок

Входные данные: LLM-запрос + веб-поиск. Процесс:
  • Запрос к LLM: «Составь максимально полный список музеев, галерей, выставочных пространств Санкт-Петербурга, где проходят выставки изобразительного искусства. Для каждого укажи: название, адрес, сайт (если знаешь), тип (музей/галерея/выставочное пространство).»
  • Серия web search запросов:
- "галереи современного искусства Санкт-Петербург"

- "музеи Санкт-Петербург выставки живописи"

- "выставочные залы Петербург"

- "art galleries Saint Petersburg"

- "все галереи Петербурга список"

- И т.д.

  • Парсинг результатов поиска, извлечение названий и URL-ов
  • Мерж LLM-списка и результатов поиска, дедупликация по названию (fuzzy)
  • Результат: seed-список ~100-200 площадок

7.2. Шаг 2: Обогащение каталога площадок

Для каждой площадки из seed-списка:

  • Загрузить главную страницу сайта
  • LLM-экстракция: адрес, часы работы, описание, контакты, ссылка на раздел «Выставки»
  • Геокодинг адреса (Яндекс Geocoder API или Nominatim) → geo_lat, geo_lon
  • Скачать логотип / фото фасада → image_url
  • Сохранить в таблицу Venue + создать Source с типом website_museum и URL раздела выставок

7.3. Шаг 3: Обнаружение телеграм-каналов

Процесс:
  • Запрос к tgstat.ru (если доступен API) или ручной веб-поиск: каналы с ключевыми словами:
- искусство Петербург, выставки СПб, галерея, музей Петербург

- Также: каналы конкретных площадок из каталога

  • Для каждого найденного канала:
- Забрать описание + последние 30 постов

- LLM оценивает релевантность: «Этот канал публикует информацию о выставках изобразительного искусства в Санкт-Петербурге?»

- Оценка 0-1, порог 0.5 для включения

  • Ранжирование по: релевантность × количество подписчиков × частота публикаций
  • Топ-N каналов → таблица Source с типом telegram_channel

7.4. Шаг 4: Каталог агрегаторов

Фиксированный список (kudago, afisha, sobaka, timeout, the-village) — вносим вручную, т.к. их мало.

Для каждого:

  • Определяем URL раздела «Выставки / СПб»
  • Проверяем наличие API (kudago имеет публичный REST API)
  • Для остальных — анализ структуры страницы (LLM помогает определить CSS-селекторы или паттерны)
  • Создаём Source с scraper_config

7.5. Еженедельное обновление

Каждое воскресенье:

  • Повторить веб-поиск на предмет новых площадок/каналов
  • Сравнить с текущим каталогом
  • Новые кандидаты → в админку на подтверждение
  • Неактивные источники (нет обновлений 30+ дней) → пометить для проверки

9. Веб-портал

9.1. Архитектурный подход

SSG (Static Site Generation) + API для поиска.
  • Основной контент (страницы выставок, площадок, художников, календарь) — генерируется статически после ежедневного пайплайна
  • Поиск и фильтрация — лёгкий API-бэкенд
  • Мобильная адаптивность (responsive design) — обязательна

9.2. Страницы и разделы

9.2.1. Главная (/)

  • Блок «Новые выставки» — последние добавленные
  • Блок «Заканчиваются скоро» — топ-5 событий, заканчивающихся в ближайшие 7 дней
  • Блок «Сейчас проходят» — общее количество + ссылка на каталог

9.2.2. Каталог выставок (/exhibitions)

  • Список выставок с фильтрами:
- Статус: идёт / скоро / анонс

- Теги (жанр, стиль)

- Площадка

- Художник

  • Сортировка: по дате начала, по дате окончания, по дате добавления
  • Карточки: изображение, название, площадка, даты, теги

9.2.3. Страница выставки (/exhibitions/{slug})

  • Полное описание
  • Изображение
  • Площадка (ссылка)
  • Даты
  • Художники (ссылки)
  • Теги
  • Источники информации

9.2.4. Каталог площадок (/venues)

  • Список площадок с фильтром по типу
  • Карточки: название, тип, адрес, кол-во текущих выставок

9.2.5. Страница площадки (/venues/{slug})

  • Описание, адрес, часы работы, фото
  • Текущие выставки
  • Прошедшие выставки (архив)

9.2.6. Каталог художников (/artists)

  • Алфавитный список
  • Поиск по имени

9.2.7. Страница художника (/artists/{slug})

  • Биография, фото
  • Связанные выставки (текущие + архив)

9.2.8. Календарь (/calendar)

  • Calendar view (месяц) — визуализация выставок по датам
  • Ось Y — площадки, ось X — даты (timeline view, gantt-подобный)
  • Read-only, без взаимодействия

9.2.9. Заканчиваются скоро (/ending-soon)

  • Список выставок, заканчивающихся в ближайшие 7 дней
  • Сортировка по дате окончания (ближайшие первые)

9.2.10. Поиск (/search?q=...)

  • Полнотекстовый поиск по: названиям выставок, площадкам, художникам, описаниям, тегам
  • Результаты с группировкой по типу (выставки / площадки / художники)

9.3. SEO

  • Канонические URL для всех сущностей
  • Meta-теги (title, description, og:image)
  • Structured data (JSON-LD): Event, Place, Person
  • Sitemap.xml, robots.txt

10. Админ-интерфейс

10.1. Доступ

Простая авторизация (логин/пароль или Telegram OAuth). На фазе 1 — один-два администратора.

10.2. Разделы

10.2.1. Дашборд

  • Всего выставок: running / announced / ended
  • Собрано сегодня: raw events → relevant → published
  • Источники: активных / с ошибками
  • Очередь модерации: N событий ждут проверки
  • График: события за последние 30 дней (собрано / опубликовано / отклонено)

10.2.2. Единая очередь задач (Pending Queue)

Единый интерфейс для всех элементов, требующих внимания администратора. Объединяет все типы pending-задач в одном месте с фильтрацией по типу:

Тип задачиОписаниеДействия
Модерация выставкиНовая выставка ожидает проверкиApprove / Reject / Edit & Approve
Новая площадкаПлощадка создана автоматически, требует подтвержденияConfirm / Edit / Delete
Новый художникХудожник создан автоматическиConfirm / Edit / Merge с существующим
Новый источникКандидат обнаружен при еженедельном сканированииAdd / Ignore
Проблемный источникИсточник не отвечает 3+ дняRetry / Disable / Delete
Возможный дубликатДедупликация не уверена (confidence 0.5-0.8)Merge / Keep separate
Конфликт данныхПротиворечивые данные из разных источниковВыбрать верный вариант

Для каждой задачи отображается:

  • Тип и приоритет
  • Дата создания
  • Контекст (сырой контент, нормализованный результат, предложенные связи)
  • Кнопки действий

Счётчик нерешённых задач по типам отображается на дашборде и в виде badge на вкладке.

10.2.3. Очередь модерации выставок (подраздел Pending Queue)

  • Список RawEvent со статусом normalized + moderation_status = pending
  • Для каждого: сырой контент, нормализованный результат, предложенные связи (площадка, художники)
  • Действия: Approve / Reject / Edit & Approve
  • При Edit — возможность исправить любые поля перед публикацией

10.2.4. Управление выставками

  • CRUD выставок
  • Ручное создание выставки
  • Изменение статуса, скрытие/показ
  • Мерж дубликатов

10.2.5. Управление площадками

  • CRUD площадок
  • Список площадок pending (созданных автоматически, но не подтверждённых)
  • Confirm / Edit / Delete

10.2.6. Управление художниками

  • CRUD художников
  • Мерж дубликатов (один художник мог быть создан под разными вариантами имени)

10.2.7. Управление источниками

  • Список всех источников с метриками:
- Статус (active / error / disabled)

- Последний успешный сбор

- Всего событий / релевантных (за всё время и за последний месяц)

- Reliability score

  • Добавление нового источника
  • Отключение / удаление источника
  • Ручной запуск сбора для конкретного источника

10.2.8. Логи пайплайна

  • Лог последнего запуска: сколько собрано, отфильтровано, нормализовано, дедуплицировано
  • Ошибки с деталями
  • Использование LLM API: количество запросов, токенов, стоимость

11.3. Поток данных (ежедневный цикл)

`

03:00 Cron запускает Scraper Service

├─ Для каждого Source → скачать контент → RawEvent (status: new)

└─ ~03:30 Все источники обработаны

03:30 Cron запускает Processor Service

├─ RawEvent (new) → LLM Relevance → (filtered)

├─ RawEvent (relevant) → LLM Normalize → (normalized)

├─ Normalized → Dedup → Exhibition create/update

└─ Exhibition → Moderation queue (или auto-approve)

[Ручная модерация — в течение дня через админку]

После модерации / автоматически:

├─ Publisher: генерация FeedPost → публикация в Telegram

└─ Publisher: триггер SSG rebuild → обновление веб-портала

10:00 (Воскресенье) Publisher: дайджест «Заканчиваются» → Telegram + pin

00:00 Cron: обновление статусов Exhibition (announced→running→ending_soon→ended)

`

11.4. LLM API Gateway

Поддерживаемые провайдеры:
  • Anthropic Claude (основной)
  • OpenAI GPT-4o (fallback)
Стратегия:
  • Primary: Claude (лучше для длинных текстов и экстракции на русском)
  • Fallback: GPT-4o (при недоступности основного)
  • Для простых задач (классификация relevance): можно использовать более лёгкие модели (Claude Haiku / GPT-4o-mini) для экономии
Мониторинг:
  • Логирование каждого запроса: модель, токены input/output, latency, стоимость
  • Дневной/месячный отчёт по расходам в админке

13. Нефункциональные требования

13.1. Производительность

МетрикаЦелевое значение
Полный ежедневный пайплайн≤ 2 часа
Загрузка веб-страницы (SSG)< 1 сек (TTFB)
Поиск< 500 мс
SSG rebuild< 5 мин

13.2. Надёжность

  • Пайплайн должен быть идемпотентным (повторный запуск не создаёт дубликатов)
  • При падении одного источника — остальные продолжают работать
  • Алертинг при: 3+ дней без успешного сбора, аномальное количество нерелевантных событий

13.3. Масштабируемость

  • Фаза 1: single server (Docker Compose)
  • Архитектура позволяет горизонтальное масштабирование Scraper и Processor (через task queue)
  • Добавление нового города = добавление Sources + Venues, без изменения кода

13.4. Безопасность

  • Админка за авторизацией
  • API keys LLM-провайдеров — в секретах (.env), не в коде
  • Telegram user session — хранить безопасно (encrypted)
  • Rate limiting на публичный API (поиск)

13.5. Стоимость LLM API — детальная оценка

Допущения:
  • ~200 источников, ~300 raw events/день (многие нерелевантные)

14. Фаза 2+ — Дорожная карта

Фаза 2: Пользовательские функции

Фокус: Персонализация и взаимодействие.
  • Авторизация — Telegram Login / email
  • Личный календарь — добавление выставок в «Хочу пойти»
  • Шеринг календаря — публичная ссылка на свой план
  • Напоминания — персональные напоминания о выбранных выставках (Telegram-бот в ЛС)
  • Отзывы — короткий отзыв + оценка после посещения
  • Отметка «Не интересно» — исключение из рекомендаций
  • Inline-кнопки в Telegram — «Хочу пойти» / «Не интересно» прямо в посте канала
  • Карта — интерактивная карта площадок с текущими выставками

Фаза 3: Рекомендации и аналитика

  • Рекомендации — на основе тегов, лайков, посещений: «Вам может понравиться»
  • Аналитика популярности — какие выставки чаще добавляют, какие площадки популярнее
  • AI-ассистент — чат-бот: «Что посмотреть в эти выходные?», «Есть ли выставки импрессионистов?»

Фаза 4: Масштабирование

  • Мультигородность — Москва, Казань, другие города
  • Расширение тематики — фотовыставки, перформансы, арт-ярмарки
  • Мультиязычность — английская версия портала
  • Партнёрства — интеграция с билетными системами, коллаборации с площадками
